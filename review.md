## Качество кода (ревью)

Это ключевая секция предназначенная для кандидатов уровня Middle, после которой мы можем определить какие секции будут следующими. При хорошем прохождении можно провести архитектурные секции с надеждой что перед нами уровень Senior или выше. Если же секция пройдена плохо, но нас устроил бы и кандидат не выше Junior или Middle-, то лучше будет сфокусироваться на знаниях конкретных технологий которые мы используем. На примере React: для сильного разработчика незнание технологии не будет проблемой, за недельку-другую освоит на хорошем уровне, а для слабого разработчика незнание технологии будет достаточно критичным минусом чтобы отказать, так как у него уйдет существенное количество времени чтобы закрыть этот пробел.

Для проведения секции презентуем следующий компонент, введя кандидата в контекст:
У нас React-приложение, в качестве стейт-менеджера используется effector, в приложении используется `@vkontakte/vkui` в качестве ui-kit. Нужно провести ревью компоненты страницы плейлиста. На странице есть шапка, футер, название плейлиста или альбома с указанием артиста, и список аудиозаписей. Данные для шапки и футера достаются из сторов.

Предлагаем кандидату провести ревью и спрашиваем "На что следует обратить внимание в этом коде? Какие правки обязательны для прохождения ревью, а какие являются рекомендациями?"

**Важно:** прежде чем кандидат начнет ревью, нужно дать понять, что тут нет чётких правильных или неправильных ответов и мы просто хотим понять что для кандидата является качественным кодом, а что некачественным, чтобы сверить это с нашими представлениями о качестве кода.

**Важно:** помним что это интервью, а не реальное ревью. Поэтому хоть и пытаемся вытянуть из кандидата внятную аргументацию предлагаемых решений, но не переводим это в холивар.

```JSX
import { useState, useEffect } from 'react';
import { useStore } from 'effector-react';
import { Title, Spinner } from '@vkontakte/vkui';

import { Logger } from '#utils/Logger';

import { fetchPlaylist } from '#api';

import { $user } from '#store/user';
import { $footerData } from '#store/footer';

import { Layout, Header, Footer, PlaylistAudios } from '#components';

export function PlaylistPage({ id }) {
  const user = useStore($user);
  const footerData = useStore($footerData);

  const [audios, setAudios] = useState([]);
  const [title, setTitle] = useState(null);

  useEffect(() => {
    const logger = new Logger();

    fetchPlaylist(id)
      .then((data) => {
        setTitle(
          [
            data.artist?.title,
            data.title,
          ].filter(Boolean).join(' - ')
        );
        setAudios(data.audios);
      })
      .catch(logger.error);
  }, [id]);

  return (
    <Layout>
      <Header user={user} />
      <div className="PlaylistPage__content">
        {!playlist && <Spinner />}
        {title && (
          <Title className="PlaylistPage__title">{title}</Title>
        )}
        {audios.length && <PlaylistAudios playlist={audios} />}
      </div>
      <Footer data={footerData} />
    </Layout>
  );
}
```

Сначала даем время кандидату самостоятельно найти проблемы с качеством кода. Когда кандидат закончит, задаем наводящие вопросы, если эти проблемы не были упомянуты:
1. Мы создаем Logger в эффекте, нет ли с этим никаких проблем?
1. Мы запрашиваем данные при помощи хелперов вроде `fetchPlaylist`. Насколько хорошо такое решение?
1. Мы загружаем данные в React-компоненте. Нормально ли это или есть более подходящие места?
    1. Если бы в приложении не было стейт-менеджера, то как можно было бы поступить не добавляя стейт-менеджер?
1. Мы форматируем заголовок страницы прямо в компоненте. Как считаешь, хорошо ли форматировать данные в React-компонентах?
    1. Если мы вынесли форматирование в отдельную функцию-форматтер, но вызывается она все равно в React-компоненте. Нет ли более подходящих мест для форматирования?
1. Нет ли проблем с обработкой ошибок?
    1. Логгирования достаточно?
1. Мы пробрасываем `className` в компоненту `Title` чтобы немного поправить стили. Не будет ли потом никаких проблем с этим?
1. Мы достаем данные о пользователе и просто пробрасываем их дальше в компоненту `Header`. Нет ли решений лучше?
1. Нет ли проблем с API компоненты `Footer`?
1. В компоненте у нас есть и верстка и работа с данными, насколько хорошее это решение?

Если кандидат не использовал принципы проектирования при ревью, то после просим оценить этот код с точки зрения SOLID или других известных принципов проектирования. Можно еще спросить какие принципы кандидат применяет в работе.

### Оценка

Тут есть несколько важных критериев из которых складывается общая оценка:
1. Количество найденных проблем
    * От сильного разработчика ожидаем нахождение большинства проблем
    * Нахождение проблем без подсказок лучше, чем с подсказками
    * Если кандидат обращает внимание только на code style, то это очень слабое ревью
1. Качество предлагаемых решений.
1. Аргументация
    * Сильный разработчик использует внятные и весомые аргументы.
    * Прошлый опыт - плохой аргумент.
    * Принципы проектирования - хороший аргумент.
    * Примеры рисков того что может пойти не так - неплохой аргумент, и чем вероятней риск тем аргумент лучше.

Незнание принципов проектирования - это не признак того, что кандидата нельзя будет оценить как Senior, но без знания принципов проектирования кандидат вероятней "посыпется" на архитектурных секциях. Поэтому если кандидат прошел секцию хорошо, но не знает принципов, даем ему шанс и проводим архитектурные секции.
