### Прерывание секции

Есть две ситуации, когда после завершения третьего этапа нет смысла продолжать.

#### Кандидат легко проходит секцию

Если вы убеждены, что кандидат предтендует на Senior, можно прерывать и переходить к Senior-секциям.


Критерии, которые могут характеризовать Senior:
* Задает правильные вопросы, в правильное время, выясняет ограничения
* Рассуждает до предложения реализации, возможно даже рассматривает различные альтернативные варианты
* Пользуется принципами и паттернами проектирования
* Чистая стилистика кода
* Адекватно воспринимает критику неудачных решений, осознает проблему и исправляет

#### Кандидат очень плохо проходит секцию

Если вы убеждены, что кандидат более не предтендует на Middle+, можно прерывать и переходить к Middle-секциям.

Критерии, которые могут подсветить несоответствие ожиданиям:
* Неспособность придумать решение. Если даже при рассуждении вслух и с вашими подсказками кандидат ходит по кругу и предлагает плохие решения, или вовсе зависает.
* Плохие решения предлагаются сильно чаще хороших. Тут важно отметить, что возможно с вашей стороны задача была донесена неправильно. Если вы убеждены, что задача была ясно понята кандидатом, то, скорее всего, у кандидата недостаток опыта.
* Непонимание или непринятие хороших решений. Если с вашими аргументацией и предлагаемым решением все в порядке, но кандидат не понимает(или, что хуже, не принимает его), то, скорее всего, у кандидата недостаток опыта.
* Не пользуется принципами проектирования
* Не пользуется паттернами проектирования и/или не понимает вас, если вы используете паттерны в критике и предложениях
* Грязный код. Подсветите кандидату проблемы со стилистикой, и то, что на этой секции это важно, возможно проблемы из-за того, что он торопится.

### Критика и споры

В процессе секции вам придется оценивать и, вероятно, критиковать предлагаемые кандидатом решения.

Всегда помните:
1. Вы - лицо компании. Кандидат - человек посторонний.
1. Это не Code Review, а интервью. Ваша цель - оценить кандидата, а не спроектировать хорошее решение.
1. Ни в коем случае не скатывайтесь в спор. Тем более в неконструктивную его версию - холивар.
1. Хорошие решения, приведенные в секции - не единственно верные.
1. Кандидат может вас не понимать, если задача была понята неправильно. Возможно вы неправильно задали вопросы, у вас недостаточно аргументов, или вы неправильно оценили решение.
1. Если вы считаете, что вы правы, но возникает спор - дайте кандидату ошибиться. Время покажет. Переходите к следующему этапу, и, если вы правы, решение кандидата где-то сломается.
1. Можно поинтересоваться, но ни в коем случае не ввязываться в спор на тему вкусовых предпочтений. Например, холивар "ООП vs ФП".
1. Критикуйте с точки зрения удобства использования, масштабируемости, тестируемости, читабельности.
1. На вашей стороне стабильноее и проверенное временем решение, а так же практики чистого кода.

### Условия и ограничения

Каждый этап секции включает в себя:
1. Условия. Это то, о чем вы сообщаете кандидату в начале этапа, ставя задачу.
1. Ограничения. Это то, о чем вы не сообщаете кандидату, пока он не **спросит прямо о конкретном ограничении**, или пока не **ошибется**.

**Если выдавать ограничения сразу, то весь смысл секции пропадает.**

Если кандидат не понял задачу, он уточняет перед реализацией - это показатель зрелого исполнителя.

Если кандидат не конкретизирует вопрос об ограничениях, а спрашивает что-то вроде *"А какие есть ограничения?"*, то не перечисляйте ограничения, а задавайте встречный вопрос *"О каких конкретно ограничениях интересуешься?"*. Отвечаем только на конкретные вопросы.

### Этап 1

```
Title: Базовый логгер

Продумать и описать интерфейс будущего логгера, предоставить реализацию и выпустить как библиотеку.
Нам достаточно трех типов логов: `info`, `warning`, `error`

В базовой реализации достаточно выводить логи в консоль.
```

Ограничения:
* `warning` и `error` должны **уметь** принимать на вход объект исключения в качестве сообщения (в JS это `Error`)
* Логгер используется на сервере, но в будущем возможно использование и в браузере (или другом окружении)
* Обработку ошибок, при невозможности залогировать, можно опустить

#### Хорошее решение

Выделит интерфейс:
```ts
interface ILogger {
  info(log: any): void;
  warning(log: any): void;
  error(log: any): void;
}
```

Использует класс для имплементации интерфейса:
```ts
class Logger implements ILogger {}
```

#### Менее удачное решение

Выделит абстрактный класс:
```ts
abstract class Logger {
  abstract public info(log: any): void;
}
```

В первоначальном условии ничего не говорилось о разных имплементациях логгера. Сейчас это усложение, нарушение KISS и YAGNI.

Абстрактный класс имеет смысл в том случае, если предполагается использование множества разных имплементаций и при этом сама абстракция содержит общую логику, вне зависимости от имплементации.

#### Плохие решения

Реализует сразу объект:
```ts
const logger: ILogger = {
  info(message: string) {
    console.log(message);
  },
  warning(message: string | Error) {
    console.log(message);
  },
  error(message: string | Error) {
    console.log(message);
  },
}
```

Вопросы:
1. Почему такое решение?
1. Что делать, если будут необходимы параметры?
1. Что делать, если будут необходимы несколько копий объекта?

Если реализация в виде функции:
```ts
function Logger() {
  return {
    info(message: string) {
      console.log(message);
    },
    warning(message: string | Error) {
      console.log(message);
    },
    error(message: string | Error) {
      console.log(message);
    },
  };
}
```

Вопросы:
1. Почему функция предпочтительнее классов?
1. Что делать, если пользователю захочется расширить функциональность? (Вопрос про наследование)

### Этап 2

```
Title: Поддержать новые способы доставки для логгера

Нужно поддержать новые способы доставки логов:
1. Отправка по HTTP
2. Запись в файл

Примечание: можно использовать псевдокод для реализации каждого способа
```

Ограничения:
* Способы доставки логов должны быть настраиваемыми

#### Хорошее решение

Паттерн "Команда"

Выделить интерфейс `ITransport` и передавать его как зависимость в `Logger`:
```ts
interface ITransport {
  send(message: string): void;
}

class ConsoleTransport implements ITransport {
  public send(message: string | Error) {
    console.log(message);
  }
}

class Logger implements ILogger {
  private transports: ITransport[];
  
  constructor(params: { transports: ITransport[] }) {
    this.transports = params.transports;
  }
}

const logger = new Logger({
  transports: [new ConsoleTransport()],
});
```

#### Менее удачное решение

Паттерн "Стратегия"

"Стратегия" очень похожа на "Команду", но в данном случае использование "Стратегии" переусложнит реализацию, ведь необходимо выделение контекста: либо логгер сам станет контекстом, либо появится промежуточный класс для контекста.

#### Плохие решения

Реализует транспорты внутри:
```ts
class Logger implements ILogger {
  private transports: ITransport[] = [];

  constructor(transports: { http: boolean; stdout: boolean; file: boolean; }) {
    this.transports = transports;
  }
  
  public error(message: string | Error) {
    if (this.transports.stdout) {
      this.console(message);
    }
  }
  
  private console(message: string | Error) {
    console.log(message)
  }
}
```

Вопросы:
1. Как бороться с разрастанием класса?
1. У каждого транспорта может появиться своя конфигурация. Что делать в таком случае?
1. Что делать, если мы захотим переиспользовать транспорты в другом логгере?
1. Как быть, если мы захотим отнаследоваться от `Logger` и при этом использовать другую реализацию транспорта?
1. Нет ли здесь нарушения SOLID-принципов?
1. Нет ли здесь нарушения DRY/KISS?

Если кандидат выделил транспорты в отдельную сущность, но создает внутри:
```ts
class Logger {
  constructor(transports: { http: boolean; stdout: boolean; file: boolean; }) {
    if (transports.stdout) {
      this.transports.push(new StdoutTransport());
    }
  }
}
```

Вопросы:
1. У каждого транспорта может появиться своя конфигурация. Что делать в таком случае?
1. Как быть, если мы захотим отнаследоваться от `Logger` и при этом использовать другую имплементацию транспорта?
1. Нет ли здесь нарушения SOLID-принципов?

### Этап 3

*Тут важно не заострять внимание на Logstash, суть не в этом.*

```
Title: Поддержать отправку в Logstash

Нужно поддержать отправку логов в Logstash

npm-пакет с Logstash-клиентом прилагается

host и port сейчас достаточно задать один раз, при старте приложения
```

Для хранения логгов решили использовать хранилище Logstash (в данном случае не стоит заострять свое внимание на этом, хранилище не играет роли). У тебя есть некий npm-пакет, который предоставляет интерфейс для работы с хранилищем. Logstash-клиент устанавливает TCP-соединение и у него есть специальный метод для отправки данных. Интерфейс выглядит следующим образом:

Дать кандидату интерфейс:
```ts
declare class LogstashClient {
  constructor(host: string, port: number);
  
  /**
   * Устанавливает соединение
   */
  public connect(): Promise<void>;
  /**
   * Запись сообщения в лог
   */
  public log(message: any): void;
}
```

Ограничения:
* Клиент использует Keep-Alive (постоянное соединение)
* Клиент отправляет логи "пачкой" (накапливает логи и отправляет раз в единицу времени)
* Клиент хранит в памяти неотправленные логи и, если оборвалось соединение, они отправятся при восстановлении соединения

#### Хорошее решение

Паттерн "Singleton"

```ts
let instance: ITransport;

interface ILogstashTransportParams {
  host: string;
  port: number;
}

class LogstashTransport implements ITransport {
  public static ensureTransport(params: ILogstashTransportParams) {
    if (!instance) {
      instance = new LogstashTransport(params);
    }

    return instance;
  }
  
  constructor({ host, port }: ILogstashTransportParams) {
    this.logstashClient = new LogstashClient(host, port);
  }
  
  public send(message: string | Error) {
    this.logstashClient.log(message);
  }
}

// Использование
const logstashTransport = LogstashTransport.createTransport({ host: 'localhost', port: 3337 });

const logger = new Logger({ transports: [logstashTransport] });
```

#### Плохое решение

Не использовал паттерн "Singleton"

Вопросы:
1. Что делать, если потребуется несколько экземпляров `Logger`? Не получится создать несколько экземпляров транспорта, ведь нельзя сделать несколько отдельных TCP-соединений с одинаковыми параметрами.
1. Сервер может повисать и обрывать соединения. Тогда будут накапливаться в разных клиентах и, когда соединение стабилизируется, каждый отправит свою "пачку" логов. Это негативно скажется на производительности.
1. Со стороны Logstash-сервера может быть ограничение на количество соединений.

### Этап 4

*Если кандидат не учел этого ранее*

```
Title: Не можем различать типы логов

Сейчас на выходе нет разницы между различными типами логов.
При выводе в файл мы не можем отличить `info`, `warning` или `error`.
Нужно исправить эту проблему.
```

Ограничения:
* В зависимости от транспорта может быть разный формат лога

#### Хорошее решение

Выделяет спецификацию, о том как должны быть оформленны логи. Это может быть, например, JSON или XML с какой-то определенной схемой.

Для реализации спецификации необходимо выделить новую сущность `IFormatter`, имплементации которой будут реализовывать уже конкретный формат.

Форматтеры могут быть двух видов:
1. Общее форматирование для всех типов
1. Отдельное форматирование для отдельных типов

Обе реализации являются адекватными, со своими плюсами и минусами. Если кандидат предложил одну из них, то необходимо поговорить с ним почему он предложил такую реализацию и какие у нее минусы.

Общее форматирование для всех типов:
```ts
// Псевдокод, так как в логах может быть '[Error]: [Object object]'

interface ILog {
  type: string;
  message: string;
}

interface IFormatter<Log> {
  format(type: string, message: string | Error): Log;
}

interface IHTTPLog {
  type: string;
  message: any;
}

class HTTPFormatter implements IFormatter<IHTTPLog> {
  format(type: string, message: any) {
    return { type, message };
  }
}
```

Отдельное форматирование для отдельных типов:
```ts
// Псевдокод, так как в логах может быть '[Error]: [Object object]'

interface IFormatter<Log> {
  info(log: any): Log;
  warning(log: any): Log;
  error(log: any): Log;
}

class StdoutFormatter implements IFormatter<string> {
  error(log: any) {
    return chalk.red(`[Error]: ${log}`);
  }
}
```

#### Менее удачное решение

Форматирование через функции-хэлперы

```ts
type TFormatter<Log> = (type: string, message: string | Error) => Log;

function fomatStdoutLog(type: string, , message: string | Error): string {
  return `[${type}]: ${log}`;
}

// Или по типу лога
type TFormatter<Log> = (message: string | Error) => Log;

function fomatStdoutErrorLog(message: string | Error): string {
  return chalk.red(`[Error]: ${log}`);
}
```

Вопросы:
1. Что делать, если для отдельного форматтера будет необходима конфигурация? Например, для логов в файл нужно будет указывать символ конца строки.

#### Плохие решения

Если кандидат предлагает реализовать отдельные методы для каждого вида логов в транспорте:

```ts
interface ITransport {
  info(message: string | Error): void;
  warning(message: string | Error): void;
  error(message: string | Error): void;
}
```

Вопросы:
1. Не размазывается ли логика между `Logger` и `Transport`? Два класса имеют одинаковый интерфейс. Теперь добавление нового типа логов затронет все реализации `ITransport`.
1. Как это поможет в случае HTTP и логов в файл?

Если кандидат предлагает реализовать отдельные API для каждого типа ошибки(например, в случае логов в файлах, файлы будут разделены по типу логов). *Подход имеет право на жизнь, но у него есть свои ограничения*

Вопросы:
1. HTTP-сервер просто проксирует логи в хранилище. При неправильной настройке транспорта может случиться так, что `error` логи можно писать в API `info` логов. В этом случае на продакшене мы не скоро обнаружим проблему.
1. Это не решает проблему `Stdout` логов, на сервере нет разницы между `console.warning` и `console.log`, все это будет писаться в `stdout`.

В конце предложить кандидату одну их подходящих реализаций.

1. Используя интерфейс логгера можно реализовывать разные имплементации, при этом настройки каждой отдельной имплементации будет отличаться.

### Этап 7

```
Title: Поддержать логгер в браузере

Сейчас логгер используется только на сервере, но теперь понадобился и в браузере.
В приложениях есть платформонезависимый shared-код в приложении, который выполняется и на сервере и в браузере.
Нужно убедиться что логгер готов к использованию в shared-коде и предоставить рекомендации по использованию.
```

В качестве примера shared-кода можно предложить React-приложение с SSR.

#### Хороший ответ

Рекомендует завязываться не на реализацию логгера, а на интерфейс `ILogger` из первого этапа.

```ts
// Было
declare function sharedService(logger: Logger): void;

// Стало
declare function sharedService(logger: ILogger): void;
```

Одним из лучших решений будет инверсия зависимостей (IoC - Inversion of Control). Можно использовать Dependency Injection, если возможно, то в коде стоит использовать DI Container:
```ts
// Shared code

class SomeService {
  constructor(@Inject('Logger') logger: ILogger) {}
  
  public sayHello() {
    this.logger.info('Hello!');
  }
}

// на сервере
DIContainer.bind<ILogger>('Logger').to(ServerLogger.createLogger);

// на клиенте
DIContainer.bind<ILogger>('Logger').to(ClientLogger.createLogger);
```

В React можно использовать контекст:
```ts
const context = React.createContext<ILogger>();
```

#### Менее комфортные решения

Service Locator - когда есть некий объект, в котором хранятся зависимости и он пробрасывается сквозь всё приложение:
```ts
interface IContext {
  logger: ILogger;
}

const context: IContext = {
  logger: Logger.createLogger(),
};

function serviceA(context: IContext) {
  const result = serviceB(context);
  
  context.logger.info('Hello');
  
  return result;
}
```

1. Какие минусы у данного подхода? Знает ли он, почему это считается плохим решением, а иногда антипаттерном?

Синглтон:
```ts
// Логгер хранится в глобальном объекте
function getLogger() {
  if (global) return global.logger;
  
  return window.logger;
}

// Либо используется сборщик, вроде webpack
function getLogger() {
  if (procces.env.IS_SERVER) {
    return require('logger/server').instance;
  } else {
    return require('logger/client').instance;
  }
}
```
